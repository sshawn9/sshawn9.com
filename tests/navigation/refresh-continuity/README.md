# 连续刷新内容与字体

- 需求：已经显示的正文在连续刷新时不消失为背景；每个新文档首次采样到正文时，实际使用的字体已经就绪，不能用备用字体或 ready 标志冒充。
- 场景：使用真实持久偏好关闭壁纸、选择浅色主题；中文博客顶部、英文代码长文深滚动；分别普通刷新与强制刷新。未注入故障的普通刷新保留浏览器缓存，强制刷新额外延迟每文档的首个独立字体文件 500ms；额外故障场景让每份文档的各字体文件连续失败两次，再恢复原资源，检查资源重试期间的画面；先以正文实际可见确认完成两次刷新，再连续快速触发八次刷新，最后等待完成。
- 像素证据：Node 端跨文档收集 CDP screencast 的合成画面，不使用会等待字体的 Playwright 截图。正文区域的局部高对比边缘必须持续存在；纯色、渐变、顶部进度条不能通过这项检查。失败时附空白帧与相邻帧。
- 刷新请求：11 次刷新必须全部得到 CDP 成功响应；跨 renderer 提交期间仅对 `Not attached to an active page` 每 20ms 重试、最多 500ms，其他错误立即失败。附件记录成功次数和瞬时重试次数。
- 字体证据：每文档通过初始化脚本的 rAF 采样，将正文可见性、实际 CSS 字体的已加载 FontFace 与 FontFaceSet.check 结果送到 Node；中文另检查实际正文汉字对应的 Noto 分片。采样不依赖生产 data-font-state 标志。
- 限制：此用例使用 Chromium CDP。screencast 可能合并合成帧，rAF 也不是显示器录像；测试证明捕获窗口中的像素与字体结果，并用受控延迟放大错误，不能替代其他浏览器的真实操作验收。

2026-09-30 额外验收：默认 Firefox 在隔离 Xvfb 窗口接受 8 次间隔约 80ms 的真实 F5，直接采样窗口像素。此前字体脚本交付版本及其字体失败重试场景均出现背景帧；它们的字体 DOM 采样仍可能全部通过。这是未解决的失败，不能将上述 Chromium 用例通过扩大为全部浏览器的连续刷新已解决。

独立字体重做后：字体准备与首次提交相关检查通过，现有连续刷新像素断言仍有失败，未将其改成允许背景帧。按部署缓存规则进行的 Chromium 与 Firefox 真实 F5 复测中，中文列表普通刷新未采到背景帧，但深滚动代码文章和强制刷新仍有背景帧；可见正文的字体采样没有失败。浏览器 load 事件不再被当作字体准备完成，已完成刷新阶段还须等待正文实际提交。
