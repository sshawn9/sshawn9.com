## 已确认、尚未修复

### A01：初始化中途失败，没有完整收尾

页面增强初始化抛错时，可能留下持续等待的导航反馈、不能再次正常挂载的页面标记，以及初始化一半的控制器资源。

- 当前代码仍在创建页面控制器之前设置 `mountedPage`；文章控制器先创建侧栏，再创建目录和媒体控制器，没有覆盖中途失败的组合清理；导航完成入口先调用 `documentReady()`，异常会跳过后续反馈收尾。
- 需要让成功挂载、部分资源回收和导航失败收尾形成完整边界，并保留错误信息。不能只让进度条消失。
- **状态：按此前决定暂缓，先讨论错误收集机制。** 错误收集只能帮助发现故障，不能代替这项生命周期修复。

源码：[page-runtime.ts](../../apps/site/src/runtime/page-runtime.ts)、[article-controller.ts](../../apps/site/src/features/article/runtime/article-controller.ts)、[navigation-coordinator.ts](../../apps/site/src/runtime/navigation-coordinator.ts)。

### D03：KV 读取或 JSON 解析失败，没有返回约定的 503

这条已从代码线索推进到本地实测：不是“照片名单不存在”，而是“读取名单这个操作本身失败”。

- 空 KV、成功解析但字段不合法：GET、HEAD、下载上报 POST 均返回现有 503，并带 `Retry-After: 60`。
- 存储内容不是合法 JSON、KV `get()` 拒绝：三个入口均直接抛出异常，跳过上述 503，共六个异常路径得到相同结果。
- 使用真实 Worker 导出函数、内存 KV 和损坏 JSON；没有联系 Cloudflare，也没有写入线上数据。结论是本站的异常返回路径缺失，不推测真实平台最终错误页的内容。

待处理：在适当的请求边界记录读取异常并返回一致的不可用响应；区分读失败与空池，不因此覆盖数据或触发访客刷新。

源码：[worker/index.ts](../../worker/index.ts) 的 `readManifest`、`handleWallpaperRequest`、`handleWallpaperDownloadRequest`。

### B05：旧壁纸还能保留，但照片淘汰后无法上报下载

浏览器的当前照片不会因为候选名单更新就强制替换；服务器却只在当前候选池中查找下载上报身份。两者有效期不同。

本地对照使用 250 张合法照片，再加入一张更新的照片：池仍为 250 张，最老的 `photo-0` 被淘汰。上报该照片返回 404，不调用上游；上报仍在池中的 `photo-249` 返回 202，并调用模拟的下载上报接口。没有访问真实 Unsplash。

客户端先完成文件下载，再发上报请求，而且不检查非成功 HTTP 状态。因此文件保存成功不代表上报成功。**待决定并实现历史照片上报身份的保留方式和有效期**，同时保留上报失败的可观察性。

源码：[Worker](../../worker/index.ts)、[当前照片与名单更新](../../apps/site/src/features/appearance/wallpaper/system.ts)、[下载和上报](../../apps/site/src/features/appearance/wallpaper/download.ts)。

## 条件性缺口：边界已验证，不能夸大自然发生概率

### D01：Plotly 创建结果晚于卸载返回时，图形没有被回收

确认的机制：组件卸载时若主图创建结果尚未交回，清理函数拿不到主图引用；恢复执行后仍创建副图，最后的 `destroyed` 检查只是退出，没有回收这两个图。

- 三组不延迟 Plotly 的观察覆盖 `newPlot` 18 次、`react` 12 次、`relayout` 18 次。调用均在下一任务／帧观察点前完成；正常完成后离开，每图都被回收，WebGL 循环已停止。这不是“未决卸载竞态测试通过”。
- 单独扣住主图创建结果，执行真实站内导航，再主动交回结果：主、副图均未执行 `purge`；主图已经脱离文档，仍保留 canvas，WebGL 循环状态未停止。兜底释放没有触发，结果来自主动释放。
- 后者是**受控时序**，证明清理边界有缺口；没有证明正常用户操作能稳定触发，也没有测量垃圾回收后的内存量。原始 `react` 等更新过程的卸载重叠，也不能用这次创建过程的控制组代替验证。

状态：低优先级条件性缺口。后续处理时补齐“结果交回时已卸载”的资源归还，并核对更新任务的销毁边界；不需要因此替换绘图库或重写交互图。

源码：[FrenetExplorer.tsx](../../packages/content-ui/src/features/frenet-explorer/FrenetExplorer.tsx) 的初始化、`flush` 和 `onCleanup`。

### D02：关闭聚焦后，迟到的旧滚动恢复可能覆盖新跳转

关闭时当前代码立即恢复一次原位置，并在下一帧再次恢复，没有判断其间是否已有新的滚动意图。

本轮两次真实快速 Escape → Home、一次等待两帧再 Home，以及聚焦中真实浏览器后退，最终位置都正确。另在关闭点击的同一轮事件里调用真实目录链接：URL 已切到目标标题，但下一帧的旧恢复执行后，页面一直留在原来的 `scrollY=5678`，目标仍在视口上方。该组人为安排了同轮操作，不代表已经复现人工双击的发生概率。

随后做了单因素对照：保持同样的关闭和目录点击顺序，只在诊断中跳过关闭安排的那一次旧滚动恢复，不跳过同步恢复、其他帧回调或目录逻辑。结果如下：

| 对照条件             | 约 1.25 秒后的滚动位置 | 目标标题                   |
| -------------------- | ---------------------- | -------------------------- |
| 原实现               | `scrollY=5678`         | 不在视口，顶部约 `-5258px` |
| 仅跳过一次迟到的恢复 | `scrollY=307`          | 在视口，顶部约 `113px`     |

这确认了旧回调覆盖新跳转的因果关系，不只是看到两个动作接近就推测冲突。**尚未确认正常人工操作的触发条件和频率。** 后续应让旧恢复在新导航／滚动意图出现后失效，同时保留普通关闭的原位置恢复；不能据此直接删掉全部恢复逻辑。

源码：[figure-focus-controller.ts](../../packages/content-ui/src/runtime/figure-focus-controller.ts) 的 `restorePagePosition`。

## 已定位的测试工具链问题

### D05：目录新标签测试会被自动化请求拦截卡住

本轮已查明具体等待链：**测试工具暂停了新标签的资源请求，却因缺少配套协议事件没有放行，页面因此无法继续加载。** 不是目录代码取消了 Ctrl 点击，也不是文字已经生成后被字体等待隐藏。

用原页面执行真实 Ctrl 点击，开启 Playwright 原始协议日志；最后六次中三次失败、三次正常。每次失败都呈现同一组证据：

| 新标签的协议事件                   | 每次失败                              | 每次正常                   |
| ---------------------------------- | ------------------------------------- | -------------------------- |
| 请求被暂停 `Fetch.requestPaused`   | 10 个：文档和 9 个子资源              | 15 个                      |
| 配套的 `Network.requestWillBeSent` | 仅文档 1 个，9 个子资源缺失           | 15 个全部配对              |
| 壁纸脚本的 `Fetch.continueRequest` | 未发送                                | 已发送，随后正常下载       |
| 新文档的 `Page.frameNavigated`     | 未出现，Playwright 一直等首次导航提交 | 正常出现并完成 Page 初始化 |

典型失败中，壁纸请求 `networkId=28678.189`、暂停 ID `interception-job-17.0` 于 `2026-09-14T19:48:39.879Z` 出现；对应会话 `75B7EBBEB9B6283508B2D11C8F74DA4A` 此后没有它的请求开始事件或放行命令。成功对照的壁纸请求 `29026.189` 则依次暂停、收到配套事件、放行、完成。已发送的初始化命令都成功返回，不是某条命令超时。

这与已安装 Playwright `1.63.0` 的实现吻合：`coreBundle.js` 中 `_onRequestPaused` 等待配对事件，页面初始化等待 `_firstNonInitialNavigationCommittedPromise`。原始协议日志在上层事件分发前就缺少这些事件，不只是诊断监听漏记。

其他对照进一步限定结论：

- 不装诊断初始化脚本也能复现；不启用请求拦截的本站四次对照正常。仅在极简页放普通链接、一个同步空脚本和标题，有／无拦截共十二次均正常，尚未得到不依赖本站页面的最小复现。
- 另一次已发布 Page 的失败停在第一个同步脚本处，DOM 没有正文、标题或样式。只撤销拦截、不刷新也不改 DOM，约 94 毫秒后恢复。此操作同时关闭 Fetch 拦截并恢复 HTTP 缓存，不能单凭它区分两者。
- 未发布 Page 的失败不因 `unrouteAll()` 恢复：源码只更新已初始化页面，原始协议也确认没有向该失败标签发送 `Fetch.disable`。因此这不是“已撤销它的拦截，仍不恢复”的反证。

**待处理的是自动化拦截与新标签初始化的配合。** 为什么协议事件缺失、具体属于 Chromium 还是它与 Playwright 的初始化交互，尚未归因到更底层。后续核对工具版本或调整测试网络隔离方式，仍须保留真实 Ctrl 点击、原页状态与目标标题断言。当前证据不支持删除同步壁纸脚本、放宽等待掩盖失败，或将此认定为普通访客也会遇到的站点故障。

相关测试：[toc-click-intent](../../tests/article/toc-click-intent/browser.spec.ts)。
