## 审计方法

- Astro ClientRouter、Unsplash API、Web Storage 与 `HTMLImageElement.decode()` 的当前官方约束。

## 必须保持的用户结果

### 主题

- 未明确选择时跟随系统；明确选择后跨刷新和站内导航保存；
- 保存主题在首个可见帧前恢复，不出现错误主题闪帧；
- 主动切换约 600 ms，背景、文字、边界和控件作为同一视觉系统过渡；
- reduced-motion 下取消装饰动画，但状态和可读性保持完整；
- 主题、景观开关、自动轮换和当前照片互不改写。

### 景观背景

- 继续保留现有默认开启、自动轮换、下一张、下载、署名和亮暗景观视觉；
- 下一张下载并解码完成前保持当前照片，之后才进行双图层交叉淡化；
- 同构建站内导航保持同一图层、照片、队列、计时器和控制器实例；
- 景观开关与完整复合背景一起过渡，四种主题/背景组合始终可读；
- 偏好跨浏览器会话，当前照片和队列只跨当前标签页刷新；
- 页面隐藏或 reduced-motion 时不自动下载、轮换或补播；
- 增强背景失败不得阻塞正文或破坏默认背景。

### 服务端边界

- Unsplash 密钥、搜索、筛选、合并和下载事件代理只存在于 Worker；
- HTML、CSS、JavaScript 和图片继续由 Static Assets 或 Unsplash 图片 CDN 提供，普通页面不进入 Worker；
- 公开清单请求只读 KV；照片池刷新只属于 cron 或明确维护流程；
- 清单失败保留旧值，公开响应保留缓存验证，页面能安全回退。

## 关键发现

### 1. 只保存 URL 不能拥有硬刷新首帧

M4.4 初审把“HTTP cache 中已有图片”误当成“新文档首帧可同步绘制图片”。真实连续刷新证伪了这一点：即使 URL 和响应都未改变，响应式选择、缓存读取和解码仍是异步步骤，偶发时序会让默认或空背景先成为一帧。

修订后的实现保存浏览器实际选择的 `currentSrc` 压缩响应字节，限制在当前标签页和 2.5 MB 二进制预算内，不重新编码，也不下载未被浏览器选择的原始大图。正常图片层仍使用远程 URL；本地副本只拥有完整文档刷新首帧。同步 Web Storage 的成本因此被限制在一个明确、可测的体验契约内，而不是扩散为通用缓存层。

### 2. 同图硬刷新与真实资源失败是两个不同条件

照片已经稳定显示并完成本地首帧事务时，其字节就在当前标签页内，网络、HTTP cache 和 CDN 不再是同图刷新首帧的前置条件。只有副本确实缺失、损坏或写入失败，且远程图片也不可用时，才进入真实降级：正文和默认背景立即可见，图片后来恢复时正常淡入一次。

因此正常同图刷新不得再走默认背景降级；真实失败也不得通过隐藏正文或无限等待来换取照片连续性。

### 3. Worker 在空 KV 时越过了访客读取边界

`handleWallpaperRequest()` 当前在清单缺失时直接执行 `refreshOnce()`，所以第一次普通 GET 会调用 Unsplash 搜索并写 KV。模块级 Promise 只能合并同一 isolate 内的并发，不能提供全球单次初始化保证。

目标行为应直接落实现有契约：公开 GET/HEAD 只读 KV；空清单返回 503 和 `no-store`；cron 或明确维护流程负责初始化和刷新。Preview/新环境的清单播种属于 M5 部署验收，不把维护权限藏回访客请求。

### 4. 现有下载上报案例窄于 Unsplash 当前定义

现有案例只允许“保存文件”上报。Unsplash 当前官方说明：当用户把照片设置到某处时也应调用 `download_location`，并建议异步执行。本站自动展示、初始随机与定时轮换仍只是被动浏览；但用户点击“下一张”后把新照片设为当前背景，已经属于主动设置，而不仅是浏览。

因此 M4.4.2 需要决定是否把成功的手动“下一张”和明确文件下载都上报一次；初始展示、自动轮换、刷新恢复和单纯开关现有照片不报告。Worker 仍只接收照片 ID，并从私有清单取得 `download_location`。

官方依据：

- <https://help.unsplash.com/en/articles/2511258-guideline-triggering-a-download>
- <https://help.unsplash.com/en/articles/2511245-unsplash-api-guidelines>

### 5. 旧控制器满足许多行为，但不是可迁移边界

旧 `wallpaper.ts` 同时负责网络缓存、manifest 重试、存储 codec、随机队列、图片 DOM、poster 生成、计时、下载、全局 action、nanostore 发布和 Swup 生命周期；`SiteChrome.tsx` 又把持久外壳、桌面/移动菜单和视觉层集中在一个 Solid 根中。直接搬运会重新建立全局可变 store 和单体控制器，违反 ADR-002 与 v2 的维护门槛。

需要保留的是已经验证的行为和算法，不是旧模块边界。

### 6. Astro 的持久外壳正好提供所需生命周期

`transition:persist` 会把现有元素移动进新文档，而不是重建；ClientRouter 同构建导航可以保持图层节点和控制器状态。目标结构把 WallpaperLayers、AppearanceControls 和其控制器放在同一个持久 SiteShell 中；NavigationCoordinator 只把当前根属性带入目标文档，不负责照片状态。跨构建仍执行完整文档导航，由小型持久状态、head 初始文档协调器和解析期壁纸 stage 恢复。

官方依据：

- <https://docs.astro.build/en/guides/view-transitions/#maintaining-state>

## 目标模块边界

目标不是建立通用状态框架，而是七个窄边界：

1. `appearance-preferences`：验证主题/景观偏好和小型 session 快照，生成唯一同步 prepaint；
2. `wallpaper-model`：Worker 与浏览器共享的公开 manifest/photo codec；
3. `wallpaper-queue`：无 DOM、无存储、可确定测试的洗牌、取图和清单协调；
4. `theme-controller`：系统监听、显式选择、600 ms 过渡和主题色；
5. `backdrop-surface/presenter`：解析期恢复、双图片层、署名、decode 与视觉提交；
6. `scenic-wallpaper-session`：manifest、队列、计时、可见性、持久化和命令串行化；
7. `appearance-controls`：语义化静态控件，只投影会话状态，不拥有第二份状态。

每个事实只有一个权威来源：偏好在 storage codec，当前运行状态在持久控制器，最终图像在持久 DOM 层，公开照片事实在 manifest，服务端秘密事实在 Worker/KV。

## 目标生命周期

### 首次或完整文档导航

1. head prepaint 同步恢复主题、景观开关、saved-photo 元数据和经过验证的首帧副本；
2. SiteShell 解析出 boot layer、持久双图片层和署名节点；boot layer 直接绘制同一照片；
3. 同一远程响应并行加载和解码，接管 boot layer 时不执行同图过渡；
4. 只有副本缺失或损坏且远程资源不可用时，完整默认页面立即可见，随后最多执行一次复合淡入；
5. 字体独立后台准备，不参与正文或壁纸的提交条件。

### 同构建站内导航

1. SiteShell、图层、控制器、队列和计时器实例保持；
2. 目标文档只继承当前 `data-theme` 与 `data-wallpaper-mode`；
3. 内容 swap 不触发 manifest、图片或主题的第二次初始化。

### 照片切换

1. 单一命令事务取得下一候选并写入非活动层；
2. 目标完成下载、decode 和首帧副本准备后，一次提交照片、署名与 session 快照；
3. 两层交叉淡化完成后清空旧层；失败、取消和快速重复操作均保留当前层；
4. 自动轮换与手动下一张复用同一激活事务，只在意图语义上决定是否上报。

## M4.4.2 已批准取舍

### D1：正常同图刷新由本地副本拥有首帧；真实失败立即显示正文

当前照片成为可见状态前，先准备当前标签页内的首帧副本。正常同图硬刷新直接绘制该副本，不依赖 URL cache 时序；副本确实不可用时，以稳定默认背景立即显示完整正文，图片随后恢复时执行一次正常景观复合过渡。该修订由 2026-08-30 再次批准的 `BCP-004` 记录。

### D2：Unsplash 下载事件语义——采用 B

保持现有行为：只有明确文件下载成功后报告；手动下一张、被动初始展示、自动轮换、刷新恢复和开关已有照片均不报告。该选择保留现有交互语义，但已知其对 Unsplash“设置背景”示例的覆盖较窄；实现和证据不得把它描述为更宽的官方语义。

除 D1 外，不改变现有视觉、控件形态或交互步骤。空清单职责越界属于实现缺陷，按现有契约修正，不作为新体验取舍。
