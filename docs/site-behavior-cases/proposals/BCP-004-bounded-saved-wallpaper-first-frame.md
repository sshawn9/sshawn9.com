# BCP-004：当前景观照片拥有刷新首帧，真实失败不阻塞正文

- 状态：已批准
- 提出日期：2026-08-29
- 批准日期：2026-08-29
- 修订批准日期：2026-08-30
- 当前是否改变契约：是
- 当前是否允许实现：是

## 受影响案例

- `scenic-wallpaper/景观模式硬刷新优先复用同一照片，慢资源不阻塞正文.md`
- `scenic-wallpaper/定时刷新失败时保留原有效清单；首次无清单时安全回退.md`

## 当前行为

初版 v2 只保存图片 URL，并假设 HTTP cache 能在硬刷新首帧同步复用该资源。真实连续刷新证明这个假设不成立：缓存命中仍要经过异步资源选择、请求与解码，偶发时序足以让默认背景或空背景先成为一帧。字体、图片或定时等待也不能反过来隐藏正文。

## 建议行为

- 当前照片完成下载和解码后，保存浏览器实际选择的 `currentSrc` 响应字节、照片元数据、URL 和队列到当前标签页的 `sessionStorage`。不重新编码图片，也不下载浏览器未选择的原始大图；只有所选响应过大或不可读时才尝试较小的恢复 URL。
- 新照片只有在首帧副本准备并成功持久化后才成为视觉上的当前照片，避免“屏幕已切换但刷新快照仍是上一张”的双重事实。
- head prepaint 同步验证并恢复首帧副本；`BackdropSurface` 在解析期直接绘制它，同时加载相同的远程响应。远程图片接管同一照片时不得淡出、淡入或露出默认背景。
- 本地副本只负责硬刷新首帧，常驻双图片层继续负责正常展示、轮换和交叉淡化；Worker/KV 的动态清单与筛选职责不变。
- 若本地副本确实不存在或损坏，且远程图片离线、被清除或 CDN 失败，立即显示结构、主题和布局完整的默认背景页面；正文不等待图片或字体。图片后来恢复时只执行一次正常景观复合淡入。
- 字体可独立后台准备并记录 `ready`/`degraded` 状态，但不得隐藏或延迟整个页面。

## 用户可观察影响

- 已经稳定显示并完成首帧副本事务的照片，在同一标签页硬刷新时不依赖 HTTP cache 时序，首帧直接保持同一照片。
- 图片副本或存储确实不可用时，正文仍立即可见，不承担装饰资源的等待成本。
- 图片稍后可用时，用户只看到稳定默认背景到完整景观背景的一次正常淡入；不会出现空白、破损图、模糊图或错误署名。

## 证据要求

1. 当前照片稳定后至少连续硬刷新六次，首帧始终为同一照片和署名，只有首帧副本或活动图片层可见，且没有同图过渡。
2. 延迟或阻断图片与字体时，首个可见帧仍是结构、主题和布局完整的页面，`body` 不被隐藏。
3. 延迟图片随后成功时只执行一次完整复合背景过渡，最终只有一个活动层。
4. 图片失败或离线时持续使用完整默认背景，不出现永久等待或错误署名；随后恢复时允许一次正常淡入。
5. 快照保存浏览器实际选中的压缩响应；不得重新编码、下载未选择的原始大图或把图片写入 Worker/KV。

## 回滚

若首帧副本读取、验证或写入失败，退回“正文和默认背景立即可见，远程图片恢复后淡入”的真实降级路径。不得用全局页面隐藏或不确定等待掩盖失败，也不得把正常同图硬刷新误判为降级。
