# 网站行为契约治理

本文规定重构期间如何解释、修改和验证 `docs/site-behavior-cases/`。它只建立治理规则，不修改任何现有网站行为。

## 当前基线

198 个案例当前全部处于生效状态。按约束对象分为三类：

| 类型               | 目录范围                                                                                                                                                                                                                            | 数量 | 含义                                                       |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---: | ---------------------------------------------------------- |
| 产品与用户体验契约 | `refresh-navigation-lifecycle`、`site-structure-responsive-visual`、`locale-theme-fonts`、`scenic-wallpaper`、`blog-tags-sidebar`、`article-sidebar-toc-versions`、`content-tags-projects-media`、`search`、`research-interactions` |  163 | 用户能观察到的内容、视觉、交互、可访问性和性能边界         |

| 验证协议           | `validation-failure-classification`                                                                                                                                                                                                 |    8 | 怎样取得证据、怎样区分故障，以及什么证据不足以宣称行为正确 |

分类只描述案例约束的对象，不代表优先级。三类案例具有相同的生效状态。

## 不把当前实现误当成产品契约

案例中出现的 `Astro`、`Swup`、`Solid`、`Pagefind`、`Cloudflare`、`Worker`、`SSR` 或“水合”等词语，按以下规则解释：

1. 如果词语只是解释当前阶段或验收手段，重构可以替换技术，但必须保留该案例要求的用户结果。
2. 如果词语表达平台安全、资源一致性或法律归属等实质约束，替换技术时必须提供等价或更强的保证。
3. 不能仅凭标题中出现某个产品名，就认定该产品永久不可替换。
4. 不能用“实现已经不同”作为删除禁止状态或降低验收标准的理由。

重构锁定技术路线后，应把以下当前技术名称改写为能力名称，但改写本身不得改变行为：

- `/_astro/` → 带内容哈希的构建资源；
- Pagefind 入口与分片 → 搜索入口、元数据与内容分片；
- Astro Dev Toolbar → 仅开发环境可用的草稿入口；
- Worker/KV → 受信任的服务端执行环境与持久存储；
- Worker Preview/Astro Preview → 实际被测的本地、构建预览和边缘预览环境。

这些只是待执行的术语去耦，不是批准更换相关行为。

## 用户可见变更审批

以下任一变化都属于必须事先讨论并获得明确批准的行为变更：

- 页面结构、尺寸、断点、字体角色、颜色、背景、图标或视觉层级；
- 动画类型、时长、触发条件、加载反馈或页面切换表现；
- 点击、键盘、触摸、拖动、滚动、焦点、历史记录或状态恢复语义；
- 内容是否出现、排序、筛选、回退、版本、语言或搜索行为；
- 无 JavaScript、慢网络、资源失败、预览、生产或回滚时的可观察结果；
- 为简化实现而删除、合并、弱化或重新解释现有能力。

技术内部变化只有在不改变上述结果时，才不需要单独的产品批准。

## 提案流程

行为变更不得直接落入实现。必须先在 `proposals/` 下记录：

1. 受影响案例的稳定路径；
2. 当前行为和建议行为；
3. 用户价值、技术原因和不改变行为的替代方案；
4. 可观察风险、失败回退和回滚方法；
5. 自动化、视觉、人工和平台证据计划；
6. 明确状态：`待讨论`、`已批准`、`已拒绝` 或 `已撤回`。

只有“已批准”提案才能修改案例语义。实现、案例、自动化测试和人工验收说明必须在同一变更中保持一致。

## 代码质量也是验收条件

通过行为测试不代表设计合格。重构代码还必须满足：

- 每类状态只有一个所有者和一个权威来源；
- 导航、字体、滚动、外壳和页面交互的生命周期边界显式可见；
- 模块通过类型化接口协作，不通过隐藏全局变量或字符串事件暗中耦合；
- 测试优先验证用户结果，只有基础设施单元测试才断言内部机制；
- 无法用清晰名称和短接口说明的复杂度，必须先重新设计或记录架构决策；
- 不为了复用少量代码制造通用框架，也不复制状态机来换取局部开发速度。

任何无法满足这些要求的 POC 都不能直接演变为生产实现。
