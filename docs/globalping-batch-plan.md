# Globalping 外层批量探测方案

## 8. GitHub Actions 与 Artifact 持久化——独立接入范围

用户已确定使用 GitHub Actions，并接受用 Artifact 在多次运行间保存累计 SQLite；不需要本地上传修改后的 Artifact。本节规定后续工作流接入时的行为，**本次未实施，具体仓库和工作流仍待确定**。

建议工作流执行顺序：

1. 串行取得同一逻辑数据库的执行权，覆盖整个恢复、执行和保存过程，不取消正在运行的写入任务。
2. 恢复最近一份成功保存、未过期且属于这套记录任务的累计数据库。以有效快照为准，不能只找上一条成功工作流；失败的探测运行也可能保存了完整的阶段性结果。
3. 取得与线上部署匹配的资源清单，传入城市文件和本次参数，执行批量工具。
4. 采集停止后，通过 SQLite 备份机制导出一致快照，包含 WAL 中已经提交的数据。
5. 成功上传新的完整数据库 Artifact，设置允许范围内的 `retention-days: 90`。

新的 Artifact 带上数据库中的全部历史。旧 Artifact 到期不影响新快照内的记录；最后一份快照仍受自身保留期限约束。

恢复失败或预期存在的历史 Artifact 已过期，应停止并报错。首次初始化必须是明确路径，不能把任何下载失败当成空库。上传步骤在已成功恢复或明确初始化数据库的前提下处理已提交结果；不能用空文件或未恢复的新库覆盖历史来源。

探测失败但存在已提交的新记录时，应尝试保存快照，同时保留探测失败的最终状态。上传失败也必须显式报错。运行器突然丢失时，尚未上传的新增记录仍可能丢失；当前方案不增加运行中远端逐条写入。

批量工具自身不调用 GitHub API、不负责下载或上传 Artifact，也不管理工作流凭据。具体 Artifact 命名、恢复选择和首次初始化接口在确认工作流接入范围后定稿。
