# Globalping 外层批量探测方案（审阅稿）

本文规划外层批量执行，不替代 [单 URL 探测与 SQLite 存储方案](globalping-redesign-plan.md)。本次只交付文档，批量程序和工作流尚未实施。

“已确认”来自用户明确要求；其余实现细节作为建议供核查。文末集中列出待确认项，实施时不能把这些建议视为已经获得确认。

## 1. 已确认的执行规则

1. 三层循环顺序固定为：**轮次 → 资源 → 城市**。
2. 最外层轮数由执行者指定，默认一次。
3. 资源列表默认读取 `apps/site/.reports/resource-inventory.json`，按 Referenced pages 从多到少执行。
4. 城市文件是 JSON 数组，每项包含 `country`、`city`；允许有 `count`，但不要求有该字段。
5. 每次测量的节点数量由 `--limit` 控制，默认 `1`。使用现有参数名 `--limit`，不是 `--limits`。
6. 每次准备探测前查询最新 SQLite。查询最近 N 天，指定资源、指定国家和城市的 HIT 次数；次数大于等于 M 时，跳过这个“资源＋城市”组合。`--skip-hit-count` 默认 `1`。
7. A 资源符合跳过条件，不影响 B 资源；不同国家或城市分别判断。
8. 次数按节点结果记录数累计。实际返回三个节点结果就保存三条记录，三个符合计数条件的 HIT 就计三次，不按测量调用去重。
9. 本次运行新写入的记录立即参与后续判断，不使用启动时冻结的历史快照。
10. 单 URL 工具继续通过官方 Globalping CLI 测量并保存结果；SQLite 继续忠实记录，不保存累计命中次数、跳过状态等策略统计。
11. 单 URL 工具已移除 `--host`、`--path`、`--query`、`--protocol`、`--port` 五个覆盖选项及对应适配。批量入口也不提供这些选项。
12. 单 URL 工具固定 GET、使用探测节点默认 DNS，已删除 `--method` 和 `--resolver`；参数只在调用入口解析一次，核心函数接收解析后的配置。安装时不再扫描帮助文本做能力兼容检查。

本次策略按城市统计，不按节点身份、ASN 或 Cloudflare 机房进一步分组。此前讨论的机房反向选点、连续 HIT、抽样等策略不属于本次规则。

## 2. 建议的命令入口与参数

新增独立批量入口，建议命名为 `npm run globalping:batch`。保留现有 `globalping:record` 的单 URL 用途。

以下命令仅说明拟定接口，当前尚不能运行：

```sh
npm run globalping:batch -- \
  --cities globalping-cn-cities.json \
  --history-days 1 \
  --skip-hit-count 1 \
  --rounds 1 \
  --limit 1
```

| 参数               | 用途                        | 默认值或建议要求                                         |
| ------------------ | --------------------------- | -------------------------------------------------------- |
| `--rounds`         | 最外层循环轮数              | `1`，正整数                                              |
| `--resources`      | 资源清单路径                | `apps/site/.reports/resource-inventory.json`             |
| `--cities`         | 城市列表路径                | 建议必填，不擅自选择中国列表或全球列表                   |
| `--history-days`   | 最近 N 天的历史查询范围     | 建议必填；有限正数，允许小数表示不足一天                 |
| `--skip-hit-count` | 触发跳过的累计次数 M        | `1`，正整数                                              |
| `--limit`          | 每次测量最多选择的节点数    | `1`，实际返回数量以 Globalping 结果为准                  |
| `--database`       | 本次读取和追加记录的 SQLite | 沿用 `apps/site/.reports/globalping/measurements.sqlite` |
| 现有测量参数       | 请求头、IPv4/IPv6 及超时等  | 由执行者给出，沿用单 URL 工具的默认值和校验              |

默认清单和数据库路径相对于项目根目录解析；执行者显式提供的相对路径相对于当前工作目录解析。固定 GET，不在城市文件中配置参数。

每次循环取当前资源 URL 和城市，分别作为单 URL 工具的 `--url`、`--from`；执行者不再单独提供这两项。其余受支持的测量参数由执行者给出，继续用参数数组调用现有工具，不拼接 shell 命令。

协议、连接端口、路径和查询参数从资源 URL 提取。历史仍按 URL、国家和城市统计，不因其他测量选项不同而自动增加统计维度。

## 3. 两份列表的读取与排序

### 3.1 资源清单

读取已有结构中的：

- `resources[].url`：本次资源 URL。
- `resourcePages[url].length`：Referenced pages 数量。

建议沿用当前 [Markdown 报告的排序实现](../apps/site/tools/resource-inventory/markdown.mjs)：引用页面数量降序，相同数量时按 URL 的 `localeCompare` 顺序排列。

引用页面数量为 0 的资源放在最后，仍参与循环。默认使用清单中的全部资源，不额外筛掉 HTML、字体或其他类型；资源 URL 去重，保留一个探测任务。

建议启动时一次性读取、验证清单：URL 必须符合现有单 URL 工具要求，资源对应的 `resourcePages` 必须是数组；损坏的清单应明确报错，不能把结构缺失当成零引用。空资源列表报错，避免输入错误被当作成功完成。

该文件须与被探测的线上部署配套；批量程序不通过重新构建网站来生成另一份资源清单。GitHub Actions 中如何取回部署配套的清单，由工作流接入部分负责。

### 3.2 城市列表

```json
[
  { "country": "CN", "city": "Shanghai" },
  { "country": "CN", "city": "Beijing", "count": 12 }
]
```

建议规则：

- 使用来源数据的国家代码和城市名称，例如 `CN`、`Shanghai`；组合成 `--from CN+Shanghai`。
- 国家代码统一大写；城市保留原名，去除输入两端空白，不自行翻译名称。
- 按文件顺序执行；按 `country + city` 去重，保留首次出现的位置。
- `count` 及其他非必要属性不参与排序、限额或节点选择。
- 缺少国家或城市、非数组、空列表应在发起测量前报错。
- 不把多个城市拼成一次测量；每次调用只有当前城市的选择条件。

城市清单是探测范围，不是固定节点身份清单。历史归属采用结果中的 `probe_country`、`probe_city`，不通过 `request_from` 字符串反推，也不把返回城市强行改成请求城市。

## 4. 历史查询与跳过判断

### 4.1 计数单位

每个符合条件的节点结果计一次。同一节点在不同测量中的 HIT 可以重复累计；不要求连续命中，后来的 MISS 不抵消仍位于时间窗口内的 HIT。

一次测量即使返回多个节点，也要先完整保存所有结果，再判断下一个任务。不会在收集到第 M 个 HIT 时中断当前测量。

### 4.2 有效 HIT 条件——待确认

建议对普通 GET 资源采用以下条件：

```sql
result_status = 'finished'
AND http_status_code = 200
AND cache_status = 'HIT'
```

HTTP 404、重定向、204、206 等结果仍照常保存，但按此建议不计入跳过次数。只接受 200 是本次资源预热策略的选择，不是声称其他 HTTP 状态不可能被缓存。

这里检查节点自身的已解析结果，不另外用 `collection_status = 'stored'` 作为隐含门槛。若一条已保存的节点结果具备完整查询字段并满足上述条件，即可计入；没有节点结果的调用记录以及字段缺失的记录不计入。

### 4.3 时间窗口——建议口径

每次判断获取新的当前时间 `now`：

```text
since = now - N × 24 小时
since ≤ measurement_created_at ≤ now
```

使用 `measurement_created_at`，它是现有程序归一化后的 UTC 测量创建时间，不冒充节点完成时间。两端均包含，缺失时间和未来时间不计入。不使用自然日边界，也不以入库时间延长旧测量的有效范围。

### 4.4 查询示例

以下 SQL 建立在第 4.2 节建议被确认的前提下；所有值使用绑定参数：

```sql
SELECT COUNT(*) AS hit_count
FROM measurements
WHERE probe_index IS NOT NULL
  AND url = :url
  AND probe_country = :country
  AND probe_city = :city
  AND measurement_created_at >= :since
  AND measurement_created_at <= :now
  AND result_status = 'finished'
  AND http_status_code = 200
  AND cache_status = 'HIT';
```

URL 使用清单中的完整字符串，包括查询参数。不会额外按构建 ID 或 CF 机房过滤，也不会认为一个城市的 HIT 自动覆盖另一个城市。

每次查询使用新读事务的当前视图，不跨整个批次持有 SQLite 读事务，否则可能持续看到旧快照。查询连接和写入连接使用同一个数据库路径；网络等待期间不持有数据库事务。

数据库不存在时，独立批量工具可通过现有存储层初始化当前结构的新库，此时历史次数为 0。已有文件打不开或结构不匹配时必须停止，不能覆盖或退回新库。Actions 的“历史恢复失败”不属于首次初始化，见第 8 节。

## 5. 三层循环与状态归属

```text
读取并验证参数、资源清单、城市清单
确定资源与城市顺序，打开历史查询连接

for 轮次 = 1 到 rounds：
    for 资源 in 已排序资源：
        for 城市 in 城市列表：
            检查是否收到中断
            获取当前时间，查询该资源、国家、城市的历史次数
            如果次数 >= M：记录本次跳过统计，继续下一个城市
            否则：用当前 URL、城市和执行参数生成测量配置，调用 recordMeasurement(config)
                  等待本次结果写入并返回
                  按异常规则决定继续或停止

关闭查询连接，输出执行汇总
```

建议第一版串行执行，同一时刻只有一次测量。这样下一次判断自然能看到前一次已经提交的记录，不需要并发任务队列或额外锁状态。

一轮只对每个资源、城市组合判断一次。不因为次数尚未达到 M 就在同一轮自动重试；增加轮次才会再次遍历。

例如 `rounds=3`、`M=1`：第一轮 MISS、第二轮 HIT，则第三轮跳过；第一轮已经 HIT，则第二、三轮均跳过。全部跳过的一轮也属于已经执行的一轮，不暗中增加轮次。

历史事实由 SQLite 持有；资源顺序、城市顺序、轮次、执行数和跳过数由本次批量进程持有。跳过只影响本次调度和终端汇总，不写成探测记录。中断后重新运行仍按历史规则判断，不另建断点表或“已执行”文件。

## 6. 异常、取消和终端输出——建议行为

| 情况                                                          | 建议行为                                                           |
| ------------------------------------------------------------- | ------------------------------------------------------------------ |
| 参数或列表无效                                                | 发起测量前报错退出                                                 |
| SQLite 查询、打开或写入失败                                   | 立即停止，非零退出；保留此前已提交的数据                           |
| 正常取得结果，但节点 failed/offline、HTTP 非 200 或缓存非 HIT | 保存原始事实并继续遍历，不计入有效 HIT                             |
| CLI 无法启动、非零退出、本地超时                              | 由单 URL 工具尽力保存本次信息后停止批次，非零退出                  |
| 输出无法解析或保留字段解析失败                                | 保存已有信息后停止，非零退出，避免在接口异常时继续批量请求         |
| Globalping API 限流导致 CLI 失败                              | 按 CLI 失败停止，不自动等待、不自动重试                            |
| SIGINT / SIGTERM                                              | 不再开始新任务，将信号交给当前调用的 AbortSignal，等待其收尾后退出 |
| SIGKILL、运行器丢失                                           | 只能保留已经提交且仍可恢复的数据，不宣称保证完成收尾               |

当前核心函数返回 `saved`、`exitCode`、`collectionStatus`、`records`、`errors` 等，外层据此控制执行。目标网站返回 HTTP 429 是一条探测结果，不能当成 Globalping API 的额度耗尽；CLI 的一般非零退出也不能直接标成限流。第一版采用统一停止 CLI 异常的方式，不额外调用 API 或通过不可靠文本猜测重试时间。

完成全部循环时，建议退出 0；它表示本次执行计划完成，不表示每个资源都已 HIT 或达到 M。节点失败数量应在汇总中显示。

终端建议保持简洁：每次实际测量输出一行轮次、资源、城市及结果概况，错误输出简短原因；每轮和批次结束汇总执行数、跳过数、保存记录数及失败节点数。默认不打印正文、证书、完整 JSON 或逐条跳过信息。

沿用现有 SQLite 索引，先验证实际查询表现，不预先增加统计表、持久化聚合、旧库兼容或迁移代码。

## 8. GitHub Actions 与 Artifact 持久化——独立接入范围

用户已确定使用 GitHub Actions，并接受用 Artifact 在多次运行间保存累计 SQLite；不需要本地上传修改后的 Artifact。本节规定接入时的行为，**是否与批量程序同次实施、落在哪个仓库和工作流，仍待确认**。

建议工作流执行顺序：

1. 串行取得同一逻辑数据库的执行权，覆盖整个恢复、执行和保存过程，不取消正在运行的写入任务。
2. 恢复最近一份成功保存、未过期且属于这套记录任务的累计数据库。以有效快照为准，不能只找上一条成功工作流；失败的探测运行也可能保存了完整的阶段性结果。
3. 取得与线上部署匹配的资源清单，传入城市文件和本次参数，执行批量工具。
4. 采集停止后，通过 SQLite 备份机制导出一致快照，包含 WAL 中已经提交的数据。
5. 成功上传新的完整数据库 Artifact，设置允许范围内的 `retention-days: 90`。

新的 Artifact 带上数据库中的全部历史。旧 Artifact 到期不影响新快照内的记录；最后一份快照仍受自身保留期限约束。

恢复失败或预期存在的历史 Artifact 已过期，应停止并报错。首次初始化必须是明确路径，不能把任何下载失败当成空库。上传步骤在已成功恢复或明确初始化数据库的前提下处理已提交结果；不能用空文件或未恢复的新库覆盖历史来源。

探测失败但存在已提交的新记录时，应尝试保存快照，同时保留探测失败的最终状态。上传失败也必须显式报错。运行器突然丢失时，尚未上传的新增记录仍可能丢失；当前方案不增加运行中远端逐条写入。

批量工具自身不调用 GitHub API、不负责下载或上传 Artifact，也不管理工作流凭据。具体 Artifact 命名、恢复选择和首次初始化接口在确认工作流接入范围后定稿。

## 9. 验收条件

使用临时数据库、固定测试时钟、模拟测量结果验证，默认不消耗 Globalping 额度。

| 验收项     | 必须证明的行为                                                                       |
| ---------- | ------------------------------------------------------------------------------------ |
| 循环顺序   | 严格按轮次、引用页数排序后的资源、城市列表顺序调用；同引用数顺序稳定                 |
| 资源范围   | 零引用资源仍执行，重复 URL 不产生重复任务                                            |
| 城市输入   | 没有 `count` 能执行；有 `count` 不改变 `--limit`；同城去重、跨国家分别保留           |
| 资源隔离   | A 在某城市达标时跳过，B 在同城未达标时仍执行                                         |
| 城市隔离   | 同 URL 的其他城市、其他国家记录不计入当前查询                                        |
| 阈值边界   | M−1 次执行，M 次和更多次数跳过；同城不同节点的合格记录累计                           |
| 多节点计数 | 一次返回三个节点时保持三条记录；其中两个合格 HIT 就只计两次                          |
| 即时读取   | 第一轮的新 HIT 能使后续轮次跳过；外部已提交的新记录也能被下一次查询读到              |
| 时间边界   | 正确处理 since 和 now 两端；范围外、未来及缺失时间不计入；判断时间随循环推进         |
| 响应条件   | 若采用建议口径，只计 finished、HTTP 200、HIT；404、206、MISS、失败节点仍保存但不计数 |
| 累计语义   | HIT 之后存在 MISS 不会清零计数；不会自动改成连续命中或只看最新一次                   |
| 轮次上限   | 达不到 M 也不会在同一轮无限重试或增加轮数                                            |
| 跳过行为   | 不启动官方 CLI，不增加 SQLite 探测记录                                               |
| 故障边界   | CLI/解析/存储异常按已确认规则停止或继续；网站 HTTP 429 不冒充 API 限流               |
| 中断       | 中断后不再调度新任务，当前调用收尾，数据库连接关闭，已提交记录保留                   |
